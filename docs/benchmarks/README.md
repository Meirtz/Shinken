# Shinken benchmarks — first-party measurements

Every number here is first-party (this repo's runtime + SDK), reproducible from the scripts
noted per section. Remote-substrate datapoints were taken over an intercontinental WAN
(~0.28 s round-trip) against a generic remote Linux sandbox; the substrate is not identified
(vendor-neutral). Raw data is in [`data/`](data/); plots are regenerated by
[`plots.py`](plots.py) into [`../assets/bench/`](../assets/bench/).

| artifact | what it measures | source |
|---|---|---|
| `data/codec_ladder.csv` | observation bytes × codec × quality × downscale (45 pts) | `devtest/bench_codec.py` (1 remote sandbox) |
| `data/concurrency.csv` | client-side threads/RSS, sync facade vs `SharedLoop`, N=1…512 | `devtest/bench_concurrency.py` (local mock servers) |
| `data/fanout_remote.csv` | end-to-end fan-out envelope, N=4/8/16 real remote sandboxes | remote fan-out probe (local harness) |
| `spikes/a11y-coverage/evidence.json` | accessibility-tree coverage by app surface | `spikes/a11y-coverage/run.sh` |

## 1. Observation bandwidth — codec ladder

One live 1920×1080 desktop frame, encoded server-side in `shinkend` and pulled over the SDK.
Lossless PNG is the default; JPEG is the opt-in lever; downscale compounds it.

![codec pareto](../assets/bench/codec_pareto.png)

**Full-resolution (1920×1080), by JPEG quality:**

| codec | KiB | × vs PNG | encode+xfer (s) |
|---|---|---|---|
| PNG (lossless) | 1804.5 | 1.0× | 0.89 |
| JPEG q95 | 276.7 | 6.5× | 0.27 |
| JPEG q90 | 168.2 | 10.7× | 0.26 |
| JPEG q80 | 87.3 | 20.7× | 0.24 |
| JPEG q70 | 73.8 | 24.5× | 0.23 |
| JPEG q60 | 66.2 | 27.3× | 0.22 |
| JPEG q50 | 61.3 | 29.4× | 0.23 |
| JPEG q30 | 52.4 | 34.4× | 0.22 |

**JPEG q80, by downscale (longer edge):**

| resolution | KiB | × vs PNG-full |
|---|---|---|
| full 1920×1080 | 87.3 | 20.7× |
| 1280×720 | 48.0 | 37.6× |
| 960×540 | 32.0 | 56.4× |
| 768×432 | 24.0 | 75.2× |
| 512×288 | 13.0 | 138.8× |

JPEG is both ~20× smaller **and** ~4× faster end-to-end than PNG (PNG's deflate dominates the
0.89 s). Downscaling to the model's real input resolution compounds the win.

![bandwidth bars](../assets/bench/bandwidth_bars.png)

### 1b. Lossless dirty-tile delta (B2)

For a *stream* (not a single frame), `shinkend` can send only changed 64-px tiles + periodic
keyframes — lossless, and cheaper on the resource-limited guest than full frames. Typing in a
terminal, 1280×800, fps=10, 81 frames/mode (local Docker sandbox, `feat-obs-delta`):

| mode | KiB/frame | × vs full-PNG | lossless |
|---|---|---|---|
| full PNG | 28.1 | 1.0× | ✓ |
| **delta-PNG** | **2.3** | **12.1×** | ✓ |
| delta-JPEG q80 | 3.0 | 9.5× | ✗ |

Lossless delta-PNG **beats** lossy JPEG on text/terminal content — the conservative,
guest-friendly default.

## 2. Concurrency — one process, many sandboxes

The client-side cost of holding N sessions in one process (the substrate-agnostic half of the
"manage 1024 sandboxes" question), against N local mock runtimes to isolate it from the network.

![concurrency](../assets/bench/concurrency.png)

| N | mode | event-loop threads | observe-all (ms) |
|---|---|---|---|
| 64 | sync facade | 64 | — |
| 256 | sync facade | 256 | — |
| 64 | `SharedLoop` | **1** | 17 |
| 256 | `SharedLoop` | **1** | 59 |
| 512 | `SharedLoop` | **1** | 121 |

The default sync facade spends **one OS thread per session** (256 sessions → 256 threads);
`shinken.SharedLoop` holds all N on **one** thread (512 sessions → 1 thread, ~130 MiB resident).
The canonical concurrent path is the async core (`aconnect` + `asyncio.gather`); `SharedLoop`
is the sync-caller convenience. (RSS for the sync facade is omitted — `ru_maxrss` is a
high-water mark and the comparison ran after the N=512 peak; threads are the clean metric.)

### 2b. End-to-end fan-out (real remote sandboxes, WAN)

One process driving N real remote sandboxes (boot → inject `shinkend` → ws proxy → SDK),
JPEG q80 @1280 observe + click per round:

| N | round wall (s) | observe p95 (s) | KiB/sandbox | boot (s) |
|---|---|---|---|---|
| 4 | 0.43 | 0.29 | 48.2 | 33.0 |
| 8 | 0.42 | 0.30 | 48.2 | 36.6 |
| 16 | 0.51 | 0.38 | 48.2 | 43.1 |

Round wall-clock stays flat 4→16 (WAN-RTT-bound, not contended); per-sandbox bytes constant.
Real N>16 is gated by substrate cost/quota, not the client — the local curve above is the
client-side scaling evidence.

### 2c. Why the codec is load-bearing at scale

Aggregate observation egress if N sandboxes each emit one frame per second:

![aggregate egress](../assets/bench/aggregate_egress.png)

At 1024 sandboxes × 1 Hz, JPEG q80 @1280 (48 KiB) projects to **~405 Mbps** — a datacenter
NIC; the same workload in PNG (1804 KiB) projects to **~15 Gbps**, infeasible anywhere. The
bandwidth lever is what makes scale-out tractable, not a nicety.

## 3. Accessibility-tree coverage (E5 / spike #2)

What fraction of each app surface is *addressable* (roled + on-screen bbox + actionable) via
the OS accessibility tree — the load-bearing assumption behind a structured-default fast path.

![a11y coverage](../assets/bench/a11y_coverage.png)

| surface | tree | nodes | pct addressable |
|---|---|---|---|
| Qt calculator | AT-SPI | 31 | **0.871** |
| chromium page | CDP | 22 | 0.227 (every labeled control resolved) |
| zenity dialog | AT-SPI (GTK) | 10 | 0.100 |
| gnome-text-editor | AT-SPI (GTK4) | 117 | 0.094 (only 33% carry a bbox) |
| xterm | AT-SPI | — | 0.000 (no tree) |
| canvas / games | — | — | unmeasured |

Tree-diff bandwidth (typing in gnome-text-editor): diff **2.0 KiB** vs full tree 10.4 KiB vs
screenshot 76.5 KiB. **Verdict:** the data supports a *hybrid* per-window structured + pixel
fallback, **not** structured-by-default — strong for Qt and browser-via-CDP, weak for GTK,
absent for terminal/canvas. D3's structured-default therefore stays Provisional.
